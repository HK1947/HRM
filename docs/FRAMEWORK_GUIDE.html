Key Insight

The src/ folder contains reusable code (pages, helpers, fixtures). The tests/ folder contains actual test specs. This separation is crucial for maintainability.

03 How It All Connects

Test Execution Flow

When you run npm test, here's what happens:

1. Configplaywright.config.ts loads
2. Setupglobal-setup.ts runs
3. FixturesPage objects injected
4. TestsSpecs execute
5. ReportResults generated

Detailed Flow Explanation

Step 1: Configuration Loads

// playwright.config.ts
export default defineConfig({
  testDir: './tests',           // Where to find tests
  workers: 4,                   // Parallel execution
  retries: 2,                   // Auto-retry on failure
  reporter: ['html', 'allure'], // Multiple reporters
  projects: [                   // Browser configurations
    { name: 'chromium', use: devices['Desktop Chrome'] },
    { name: 'firefox', use: devices['Desktop Firefox'] },
  ],
});

Step 2: Global Setup Runs Once

// global-setup.ts
async function globalSetup() {
  // Login once and save session to auth/admin.json
  // All tests reuse this authenticated state
  const browser = await chromium.launch();
  const page = await browser.newPage();
  await page.goto('https://opensource-demo.orangehrmlive.com');
  await page.fill('[name="username"]', 'Admin');
  await page.fill('[name="password"]', 'admin123');
  await page.click('button[type="submit"]');
  await page.context().storageState({ path: 'auth/admin.json' });
}
Q: Why use global setup instead of logging in each test?

A: "Global setup runs once before all tests, saving authentication state to a file. Each test then loads this state instantly instead of repeating the login flow. This makes tests 10x faster and more reliable."

Step 3: Fixtures Inject Dependencies

// src/fixtures/index.ts
export const test = mergeTests(pageFixtures, authFixtures);

// In your test file:
import { test, expect } from '../../src/fixtures';

test('dashboard loads', async ({ loginPage, dashboardPage }) => {
  // loginPage and dashboardPage are automatically injected!
  await dashboardPage.navigate();
});

Step 4: Page Objects Handle Actions

// src/pages/login.page.ts
export class LoginPage extends BasePage {
  // Locators defined once
  private usernameInput = this.page.locator('[name="username"]');
  private passwordInput = this.page.locator('[name="password"]');
  private submitButton = this.page.locator('button[type="submit"]');

  // Reusable action
  async login(credentials: { username: string; password: string }) {
    await this.usernameInput.fill(credentials.username);
    await this.passwordInput.fill(credentials.password);
    await this.submitButton.click();
  }
}

05 Component Deep Dive

Page Object Model (POM)

Every page in the app has a corresponding class that encapsulates its locators and actions.

// src/pages/base.page.ts - All pages extend this
export class BasePage {
  constructor(protected page: Page) {}

  async waitForPageLoad() {
    await this.page.waitForLoadState('networkidle');
  }
}

// src/pages/dashboard.page.ts
export class DashboardPage extends BasePage {
  readonly sidebar: SidebarComponent;  // Composition
  readonly table: TableComponent;

  constructor(page: Page) {
    super(page);
    this.sidebar = new SidebarComponent(page);
    this.table = new TableComponent(page);
  }

  async navigate() {
    await this.page.goto('/dashboard/index');
    await this.waitForPageLoad();
  }
}
Q: Why use Page Object Model?

A: "POM provides three benefits: (1) Maintainability - if a locator changes, I update one place, not 50 tests. (2) Readability - tests read like user actions: loginPage.login() not page.fill().click(). (3) Reusability - the same login method works across all tests."

Fixtures (Dependency Injection)

Fixtures automatically create and inject page objects into tests.

// src/fixtures/page.fixtures.ts
export const pageFixtures = base.extend<PageFixtures>({
  loginPage: async ({ page }, use) => {
    const loginPage = new LoginPage(page);
    await use(loginPage);  // Inject into test
  },
  dashboardPage: async ({ page }, use) => {
    const dashboardPage = new DashboardPage(page);
    await use(dashboardPage);
  },
});

// In test - automatically receives loginPage and dashboardPage
test('verify dashboard', async ({ loginPage, dashboardPage }) => {
  await dashboardPage.navigate();
});
Q: What are Playwright fixtures?

A: "Fixtures are Playwright's dependency injection system. Instead of creating page objects manually in each test, fixtures create them once and inject them. This ensures proper setup/teardown, enables parallel execution, and makes tests cleaner."

Accessibility Testing (axe-core)

// src/helpers/accessibility.ts
import AxeBuilder from '@axe-core/playwright';

export class AccessibilityChecker {
  async analyze(options = {}) {
    const results = await new AxeBuilder({ page: this.page })
      .withTags(['wcag21aa'])  // WCAG 2.1 AA standard
      .analyze();
    return results.violations;  // Returns accessibility issues
  }
}

// In test
test('login page is accessible', async ({ page }) => {
  const a11y = new AccessibilityChecker(page);
  const violations = await a11y.analyze();
  expect(violations).toHaveLength(0);  // No issues
});

export class PerformanceAnalyzer {
  async collectMetrics() {
    return {
      largestContentfulPaint: /* LCP - main content visible */,
      firstContentfulPaint:   /* FCP - first paint */,

  const perf = new PerformanceAnalyzer(page);
  const metrics = await perf.collectMetrics();

06 Key Patterns Explained

Multi-Tab/Window Handling

test('handle new tab', async ({ page, context }) => {
  // Wait for popup BEFORE clicking
  const [newPage] = await Promise.all([
    context.waitForEvent('page'),  // Catches the new tab
    page.click('a[target="_blank"]')  // Triggers the new tab
  ]);

  await newPage.waitForLoadState();
  await expect(newPage).toHaveTitle(/New Page/);
  await newPage.close();
});

Network Mocking

test('mock API response', async ({ page }) => {
  // Intercept API call and return fake data
  await page.route('**/api/employees', route => {
    route.fulfill({
      status: 200,
      body: JSON.stringify({ employees: [{ name: 'Test' }] })
    });
  });

  await page.goto('/employees');
  // Page now shows mocked data
});

Visual Regression

test('login page looks correct', async ({ page }) => {
  await page.goto('/login');

  // First run: creates baseline screenshot
  // Subsequent runs: compares to baseline
  await expect(page).toHaveScreenshot('login-page.png', {
    maxDiffPixels: 100  // Allow small differences
  });
});

Soft Assertions

// Collect ALL failures instead of stopping at first
test('validate form fields', async ({ page }) => {
  const softAssert = new SoftAssert();

  softAssert.check(await field1.isVisible(), 'Field 1 visible');
  softAssert.check(await field2.isVisible(), 'Field 2 visible');
  softAssert.check(await field3.isVisible(), 'Field 3 visible');

  softAssert.assertAll();  // Throws with ALL failures at end
});

07 Interview Q&A Reference

Q: Explain your framework architecture

A: "It's a modular POM framework with four layers: (1) Pages - encapsulate UI elements and actions, (2) Fixtures - dependency injection for pages, (3) Helpers - utilities like retry, a11y, performance, (4) Tests - organized by type (UI, API, visual). Configuration is centralized in playwright.config.ts with environment-specific .env files."

Q: How do you handle flaky tests?

A: "Three strategies: (1) Built-in retries in config with exponential backoff, (2) Proper waits using Playwright's auto-waiting instead of arbitrary sleeps, (3) Circuit breaker pattern that stops retrying after threshold. I also tag flaky tests with @flaky to exclude from CI while investigating root cause."

Q: How do you run tests in parallel?

A: "Playwright runs tests in parallel by default. I use fullyParallel: true in config for maximum parallelism. In CI, I use sharding: --shard=1/4 splits tests across 4 machines. Each test gets an isolated browser context, so they can't interfere with each other."

Q: How do you test accessibility?

A: "I integrate axe-core which tests against WCAG 2.1 AA standard automatically. It checks 50+ rules including color contrast, missing alt text, keyboard navigation. I fail CI on critical/serious issues but log moderate ones as warnings. The helper generates detailed reports showing exactly which elements have issues."

Q: How do you handle test data?

A: "Three approaches: (1) Factory pattern with Faker.js generates unique data each run, (2) API seeding creates data before UI tests (faster than UI setup), (3) Cleanup in afterAll removes test data. Each test creates its own data for isolation - I never depend on existing database state."

Q: Explain your CI/CD pipeline

A: "GitHub Actions with three stages: (1) PR trigger runs smoke tests on Chromium only (<5 min feedback), (2) Merge to main runs full regression across Chrome/Firefox/Safari with 4-way sharding, (3) Nightly runs a11y, performance, and visual tests. Reports are merged from shards and deployed to GitHub Pages."

Q: How do you handle multiple environments?

A: "Environment config is externalized in .env files (.env.dev, .env.staging, .env.prod). The environment.ts helper loads the right one based on ENV variable. URLs, timeouts, and feature flags differ per environment. I run tests with ENV=staging npm test."

Q: What's the difference between fixtures and page objects?

A: "Page objects encapsulate UI structure and actions - they're classes with methods like login(). Fixtures are Playwright's DI system that instantiates and injects those page objects into tests. Fixtures also handle setup/teardown lifecycle. You define pages; Playwright manages fixtures."
