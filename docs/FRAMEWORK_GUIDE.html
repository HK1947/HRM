  // Login and save session to auth/admin.json
  // All tests reuse this - no repeated logins!

// Step 3: Fixtures inject dependencies

  // loginPage and dashboardPage are auto-created!

Key Patterns

📄

Page Object Model

Each page has a class with locators and actions. Changes to UI only need updates in one place.

💉

Fixtures (DI)

Playwright auto-creates and injects page objects. Tests stay clean and focused.

📊

Data-Driven

Same test logic runs with different data sets. Maximum coverage, minimal code.

♿

Accessibility

axe-core tests WCAG 2.1 AA compliance. Catch issues before they reach production.

⚡

Performance

Collect Core Web Vitals (LCP, FCP, CLS). Ensure fast user experience.

🔄

Retry + Circuit Breaker

Exponential backoff for flaky operations. Circuit breaker prevents cascade failures.

🖼️

Visual Testing

Screenshot comparison catches CSS bugs. Per-browser baselines handle rendering differences.

🌐

Network Mocking

Intercept API calls and return fake data. Test edge cases without backend changes.

Code Example: How Fixtures Work

// src/fixtures/page.fixtures.ts
export const pageFixtures = base.extend<PageFixtures>({
  loginPage: async ({ page }, use) => {
    const loginPage = new LoginPage(page);
    await use(loginPage);  // Inject into test
  },
});

// In your test file:
import { test, expect } from '../../src/fixtures';

test('login works', async ({ loginPage }) => {
  // loginPage is automatically injected!
  await loginPage.navigate();
  await loginPage.login({ username: 'Admin', password: 'admin123' });
});

Interview Q&A

Explain your framework architecture
"It's a 5-layer modular architecture: (1) Test Layer - organized by type (UI, API, a11y, visual), (2) Fixture Layer - dependency injection for page objects, (3) Page Object Layer - encapsulates UI elements and actions, (4) Helper Layer - utilities like retry, accessibility, performance, (5) Infrastructure - config, reporters, CI/CD. This separation makes tests maintainable and scalable."
Why use Page Object Model?
"Three reasons: (1) Maintainability - if a locator changes, I update one file, not 50 tests. (2) Readability - tests read like user actions: loginPage.login() not page.fill().click(). (3) Reusability - the same login method works across all tests."
What are Playwright fixtures?
"Fixtures are Playwright's dependency injection system. Instead of creating page objects manually in every test, fixtures create them once and inject them automatically. This ensures proper setup/teardown lifecycle, enables parallel execution with isolation, and keeps tests clean."
How do you handle flaky tests?
"Three strategies: (1) Built-in retries with exponential backoff - wait longer between each attempt. (2) Proper waits using Playwright's auto-waiting instead of arbitrary sleeps. (3) Circuit breaker pattern that stops retrying after a threshold to prevent cascade failures. I also tag flaky tests with @flaky to exclude from CI while investigating."
How do you run tests in parallel?
"Playwright supports parallelism at multiple levels: (1) fullyParallel: true runs test files AND tests within files in parallel. (2) In CI, I use sharding: --shard=1/4 splits tests across 4 machines. Each test gets an isolated browser context with its own cookies/storage, so they can't interfere with each other."
How do you test accessibility?
"I integrate axe-core which tests against WCAG 2.1 AA automatically. It checks 50+ rules including color contrast (4.5:1 ratio), missing alt text, keyboard navigation, and ARIA roles. I fail CI on critical/serious issues but log moderate ones as warnings. The helper generates detailed reports showing which elements have issues and how to fix them."
Explain your CI/CD pipeline
"GitHub Actions with progressive testing: (1) PR trigger runs smoke tests on Chromium only for fast feedback (<5 min). (2) Merge to main runs full regression across Chrome/Firefox/Safari with 4-way sharding. (3) Nightly schedule runs accessibility, performance, and visual tests. Reports are merged from shards and deployed to GitHub Pages."
How do you handle multiple environments?
"Environment config is externalized in .env files - .env.dev, .env.staging, .env.prod. The environment.ts helper loads the right one based on the ENV variable. URLs, timeouts, retry counts, and feature flags differ per environment. I run tests with ENV=staging npm test."
