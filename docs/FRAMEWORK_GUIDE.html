Framework Architecture

The framework uses a layered architecture where each layer has specific responsibilities. Tests import fixtures, which inject page objects, which use helpers for common operations.

Layer Responsibilities

🧪

Test Layer

Spec files organized by type: UI, API, accessibility, performance, visual regression.

💉

Fixture Layer

Dependency injection. Creates page objects and manages auth state automatically.

📄

Page Object Layer

Encapsulates locators and actions. One class per page/component.

🔧

Helper Layer

Utilities: accessibility checker, performance metrics, retry logic, test data factory.

Test Execution Flow

When you run npm test, Playwright loads config, runs global setup once, then executes tests in parallel with injected fixtures.

Key Insight

Global setup logs in once and saves cookies to auth/admin.json. Every test loads this file instead of logging in again. This makes tests 10x faster.

Key Patterns

📄

Page Object Model

Locators and actions in classes. UI change = update 1 file, not 50 tests.

💉

Fixtures (DI)

Playwright creates page objects. Tests just declare what they need.

📊

Data-Driven

Same test, different data. Loop over array of test cases.

♿

Accessibility

axe-core checks WCAG 2.1 AA. 50+ rules automatically.

⚡

Performance

Collect LCP, FCP, CLS. Assert against thresholds.

🔄

Retry + Circuit Breaker

Exponential backoff. Stop after N failures.

🖼️

Visual Testing

Screenshot comparison. Per-browser baselines.

🌐

Network Mocking

Intercept API calls. Return fake data.

Interview Q&A

Q: Explain your framework architecture
"5-layer architecture: (1) Test Layer - specs by type (UI, API, a11y, visual). (2) Fixture Layer - dependency injection for page objects. (3) Page Object Layer - encapsulates locators and actions. (4) Helper Layer - utilities (retry, accessibility, performance). (5) Core - Playwright engine. Each layer only talks to adjacent layers."
Q: Why use Page Object Model?
"Three reasons: (1) Maintainability - locator changes in one file, not 50 tests. (2) Readability - loginPage.login() is clearer than raw Playwright calls. (3) Reusability - same method across all tests."
Q: What are Playwright fixtures?
"Dependency injection system. Fixtures create page objects and inject them into tests automatically. Benefits: proper setup/teardown lifecycle, test isolation (each test gets fresh instances), parallel execution without conflicts, clean test code."
Q: How do you handle flaky tests?
"Multiple strategies: (1) Auto-retries with exponential backoff. (2) Playwright's auto-waiting instead of sleep(). (3) Circuit breaker stops retrying after threshold. (4) Tag @flaky to exclude from CI while investigating. (5) Trace/video capture on failure for debugging."
Q: How do you run tests in parallel?
"Three levels: (1) fullyParallel: true - files and tests run parallel. (2) workers: 4 - 4 browser instances. (3) CI sharding: --shard=1/4 splits across machines. Each test gets isolated browser context with own cookies/storage."
Q: How do you test accessibility?
"axe-core integration. Tests WCAG 2.1 AA: color contrast (4.5:1), alt text, keyboard nav, ARIA roles. Run await axe.analyze(), assert no violations. CI fails on critical/serious; logs moderate as warnings."
Q: Explain your CI/CD pipeline
"GitHub Actions, progressive: (1) PR - smoke on Chromium only (<5 min). (2) Merge - full regression, Chrome/Firefox/Safari, 4-way sharding. (3) Nightly - a11y, performance, visual. Reports merged and deployed to GitHub Pages."
Q: How do you handle test data?
"Three approaches: (1) Factory with Faker.js - unique data each run. (2) API seeding - create via backend before UI tests. (3) Cleanup in afterAll - delete test data. Each test owns its data; never depend on existing DB state."
