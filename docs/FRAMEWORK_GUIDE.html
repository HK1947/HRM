Framework Architecture

The framework follows a layered architecture pattern where each layer has specific responsibilities. Tests sit at the top and use fixtures to get page objects, which use helpers for common operations.

Test Execution Flow

When you run npx playwright test, this is the sequence of events that occurs. Understanding this flow is crucial for debugging and interview discussions.

Test Execution Sequence Diagram
sequenceDiagram
    participant Dev as Developer
    participant PW as Playwright
    participant GS as Global Setup
    participant FIX as Fixtures
    participant PO as Page Objects
    participant APP as OrangeHRM App

    Dev->>PW: npx playwright test
    PW->>PW: Load playwright.config.ts
    PW->>GS: Run global-setup.ts
    GS->>APP: Login as Admin
    APP-->>GS: Return session cookies
    GS->>GS: Save to auth/admin.json
    GS-->>PW: Setup complete

    loop For each test file (parallel)
        PW->>FIX: Initialize fixtures
        FIX->>FIX: Load auth state from JSON
        FIX->>PO: Create page objects
        PO-->>FIX: Return loginPage, dashboardPage, etc.
        FIX-->>PW: Inject fixtures into test

        PW->>PO: test calls page.navigate()
        PO->>APP: Navigate to page
        APP-->>PO: Page loaded

        PO->>APP: Perform actions (click, fill, etc.)
        APP-->>PO: Return results

        PW->>PW: Run assertions
        PW->>PW: Capture screenshots/traces on failure
    end

    PW->>PW: Generate reports (HTML, Allure, JUnit)
    PW-->>Dev: Show results

Best Way to Learn

Run npm run test:ui to open the visual test runner. You can browse all tests, run them individually, and watch the browser in real-time. This is the fastest way to understand how the framework works.

Key Patterns

📄

Page Object Model

Encapsulate locators and actions in classes. If UI changes, update one file instead of every test.

💉

Fixtures (DI)

Playwright creates and injects page objects automatically. Tests stay clean and focused.

📊

Data-Driven Testing

Same test logic runs with different data sets. Maximum coverage with minimal code.

🔄

Retry + Circuit Breaker

Exponential backoff for flaky operations. Circuit breaker prevents cascade failures.

Interview Q&A

Q: Explain your framework architecture
"It's a 5-layer architecture: (1) Test Layer - specs organized by type (UI, API, a11y, visual), (2) Fixture Layer - dependency injection for page objects, (3) Page Object Layer - encapsulates UI elements and actions, (4) Helper Layer - utilities like retry, accessibility, performance, (5) Core - Playwright engine. Each layer only communicates with adjacent layers, making it maintainable and testable."
Q: Why use Page Object Model?
"Three reasons: (1) Maintainability - if a locator changes, I update one file, not 50 tests. (2) Readability - tests read like user actions: loginPage.login() not page.fill().click(). (3) Reusability - the same login method works across all tests without duplication."
Q: What are Playwright fixtures and why use them?
"Fixtures are Playwright's dependency injection system. Instead of creating page objects manually in each test, fixtures create them once and inject them automatically. Benefits: (1) Proper setup/teardown lifecycle, (2) Test isolation - each test gets fresh instances, (3) Parallel execution without conflicts, (4) Clean test code without boilerplate."
Q: How do you handle flaky tests?
"Multiple strategies: (1) Auto-retries with exponential backoff - wait 1s, 2s, 4s between attempts. (2) Proper waits - use Playwright's auto-waiting instead of sleep(). (3) Circuit breaker - stop retrying after threshold to fail fast. (4) @flaky tag - exclude from CI while investigating root cause. (5) Trace on failure - capture video, screenshots, network for debugging."
Q: How do you run tests in parallel?
"Playwright supports parallelism at multiple levels: (1) fullyParallel: true runs test files AND tests within files in parallel. (2) workers: 4 sets concurrent browser instances. (3) In CI, sharding: --shard=1/4 splits tests across 4 machines. Each test gets an isolated browser context with its own cookies/localStorage, so they can't interfere."
Q: How do you test accessibility?
"I integrate axe-core for automated WCAG testing. It checks 50+ rules including color contrast (4.5:1 ratio), missing alt text, keyboard navigation, ARIA roles. I run await axeBuilder.analyze() and assert no violations. CI fails on critical/serious issues; moderate ones are logged as warnings. Reports show exactly which elements fail and how to fix them."
Q: Explain your CI/CD pipeline
"Progressive testing in GitHub Actions: (1) PR - smoke tests on Chromium only (<5 min feedback). (2) Merge to main - full regression across Chrome/Firefox/Safari with 4-way sharding. (3) Nightly - accessibility, performance, visual tests. Reports are merged from shards using playwright merge-reports and deployed to GitHub Pages for team visibility."
Q: How do you handle test data?
"Three-pronged approach: (1) Factory pattern with Faker.js generates unique data each run - no collisions. (2) API seeding creates data via backend before UI tests - faster than UI setup. (3) Cleanup in afterAll removes test data to prevent pollution. Each test creates its own data for isolation - I never depend on existing database state."
